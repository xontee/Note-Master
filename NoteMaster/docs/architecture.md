# Архитектура NoteMaster Core

## Слои

| Слой | Модули | Ответственность |
|---|---|---|
| Core | `app/core` | Конфигурация и иерархия исключений |
| Models | `app/models` | Доменные модели, валидация, сериализация |
| Storage | `app/storage` | JSON-документ и физические файлы |
| Repositories | `app/repositories` | Доступ к заметкам через абстракцию |
| Attachments | `app/attachments` | Валидация файлов и сигнатур |
| Services | `app/services` | Бизнес-логика и координация |
| Utils | `app/utils` | Даты, размеры, теги, резервные копии |
| CLI | `app/cli` | Экраны, меню, навигация, вывод |
| Composition | `app/main.py` | Сборка зависимостей |

Зависимости направлены «внутрь»: CLI зависит от сервисов, сервисы — от
абстракций репозитория и хранилища, а конкретные реализации подставляются в
композиционном корне.

## CLI-слой

CLI разделён на четыре части, каждая со своей ответственностью:

| Часть | Модули | Ответственность |
|---|---|---|
| Компоненты | `components/console.py`, `formatting.py`, `tables.py`, `prompts.py` | Единый вывод, ширина кириллицы, таблицы, ввод и валидация формата |
| Навигация | `menu.py`, `navigation.py` | Описание меню, команда `Nav`, стек экранов `Navigator` |
| Сценарии | `handlers/` | Сбор пользовательского ввода и вызовы сервисов |
| Экраны | `views/` | Отрисовка состояния и обработка команд меню |

`AppContext` (`cli/context.py`) — это контейнер зависимостей: конфигурация,
сервисы, `Console`, `Prompter`, handlers и `Navigator`. Он создаётся один раз
в `NoteMasterCLI` и передаётся экранам, поэтому экраны не создают сервисы и
не читают настройки самостоятельно.

### Навигация

Экран не знает, кто его открыл. Он возвращает `Nav`:

- `STAY` — остаться на экране;
- `BACK` — вернуться к предыдущему экрану;
- `HOME` — вернуться на Dashboard, сбросив вложенные экраны;
- `EXIT` — завершить приложение.

`Navigator` хранит стек экранов и интерпретирует эти команды. Команда `0`
означает «назад», но на Dashboard — «выход» (`BaseView.zero_nav`). Команды
`M` и `Q` обрабатываются единообразно на всех экранах.

### Обработка ошибок

Все исключения Core наследуются от `NoteMasterError`. `BaseView._guard`
перехватывает их и передаёт в `AppContext.report_error`, который превращает
исключение в понятное сообщение (`formatting.describe_error`). Технический
traceback показывается только при `Config.debug=True`. Пустых `except` в CLI
нет.

### Вывод

`Console` — единственная точка вывода. Он:

- включает цвета только для интерактивного терминала (и учитывает `NO_COLOR`);
- включает ANSI-режим в консоли Windows;
- считает ширину строки в терминальных колонках, поэтому кириллица не ломает
  таблицы;
- подстраивает ширину таблиц под терминал, сжимая самые широкие колонки.

## Поток данных

1. Пользователь вводит команду; экран (`views`) передаёт её handler-у.
2. Handler собирает данные и вызывает метод сервиса.
3. Сервис валидирует входные данные через модель или валидатор.
4. Сервис вызывает репозиторий/хранилище.
5. Репозиторий преобразует модели в JSON-совместимые словари и делегирует
   запись `JsonStorage`.
6. `JsonStorage` пишет во временный файл и атомарно подменяет целевой.
7. Handler показывает результат через `Console`.

## Инварианты

- `Note.id` и `Attachment.id` — UUID.
- Временные метки timezone-aware (UTC).
- `updated_at >= created_at`.
- Теги уникальны без учёта регистра.
- Заголовок не пустой (до 200 символов).
- Оригинальное имя файла отделено от физического имени.
- В JSON нет содержимого файлов и абсолютных путей.
- Повреждённый JSON не перезаписывается автоматически.

## Сценарии сбоев

### Добавление вложения

1. Проверяется существование заметки и лимиты.
2. Файл валидируется (размер, расширение, сигнатура).
3. Файл копируется в хранилище через временный `.part` и `os.replace`.
4. Метаданные добавляются в заметку и сохраняются.
5. Если сохранение метаданных упало — скопированный файл удаляется
   (best-effort), ошибка пробрасывается.

### Удаление вложения

1. Находятся заметка и вложение.
2. Физический файл удаляется; если его нет — шаг пропускается.
3. Метаданные удаляются и сохраняются.
4. Если удаление файла упало — метаданные не меняются, ошибка видна.

### Удаление заметки

1. Запись заметки удаляется из репозитория атомарно.
2. Физические файлы удаляются best-effort.
3. Сбои очистки возвращаются в `DeleteNoteResult.failed_attachments`,
   а оставшиеся файлы обнаруживаются проверкой целостности как «сироты».
   Данные заметки при этом не теряются незаметно.

## Точки расширения

- `NoteRepository` — замена JSON на SQLite/PostgreSQL.
- `AttachmentStorage` — замена локального хранилища на S3/облако.
- `Note.matches` и `NoteRepository.search` — переход к полнотекстовому поиску.
- `IntegrityService` — расширение отчёта и автоматическое восстановление.
- `app/utils/backup.py` — версионирование и плановое резервное копирование.
- `app/cli/views` — новый экран достаточно зарегистрировать в `Navigator`;
  сервисы и обработка ошибок при этом не меняются.
- `app/cli/components` — замена `Console` на другой рендерер (например, Rich)
  не затрагивает handlers и views, если сохранить публичные методы вывода.
